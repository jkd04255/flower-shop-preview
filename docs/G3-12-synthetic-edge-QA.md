## G3-11에서 실제 재현한 예외

1. **불일치한 입금/예약 상태 복원:** `confirmed + waiting` 조합을 `restoreDemoBookings()`가 정상 복원함. 실제로 확인되지 않은 입금이 확정처럼 표시될 수 있어 부적절.
2. **151건 저장 후 기록 소실:** `mockNewAdminRequest()`가 새 기록 생성을 제한하지 않는데 `restoreDemoBookings()`는 150건 초과를 무효로 처리함. 150→151건 생성 뒤 새로고침하면 샘플 데이터로 초기화되는 현상 재현.
3. **7자리 가상 예약번호로 복원 실패:** `DEMO-999999` 기록은 복원되지만 다음 `mockNewAdminRequest()`에서 `DEMO-1000000`을 생성하고, 이후 복원 시 ID 정규식과 불일치해 초기화되는 현상 재현.
4. **정원 초과된 복원 기록의 달력 문구:** 정원 4/3건 데이터에서도 안내가 항상 '3/3'으로 고정됨.
5. **다른 탭에서 정원이 변경되는 경우:** 동일 브라우저의 다른 탭에서 가상 예약 상태를 변경해도 열린 고객 예약 폼의 시간 선택 목록은 갱신되지 않음. 제출 단계에서만 다시 검증.
6. **다른 탭에서 예약 기록 초기화:** 이미 보고 있는 가상 송금 완료 버튼이 이전 요청을 참조해도 시연 상태 안내가 갱신되지 않음.

## G3-12 최소 범위 수정

- 기존 **가상 데이터** 기록만 보존·복원하며, 유효한 과거 151건까지 포함하는 최대 500건 한도를 명확히 일치시킴. 500건 이상에서 새 생성은 차단하고 기존 기록은 삭제하지 않음. 구형 501건 이상 자료나 손상된 형식은 기존처럼 기본 샘플로 fail-closed.
- 6자리 예약번호 최댓값(999999)을 넘는 가상 ID를 만들지 않음. 차단 시 고객 폼에 안내 문구를 표시하고 성공 화면으로 이동하지 않음.
- 복원할 때 `confirmed/ready/completed`는 `paymentState === verified`, `pending/rejected`는 `verified` 불허, `waiting + depositChecked` 동시 참을 불허. G3-11 정상 샘플 확정건에서 `depositChecked` 생략은 유지.
- 예약 캘린더는 실제 합성 카운트(예: 4/3)를 표시하고 정원 초과를 경고하되 기존 예약을 임의로 삭제·거절하지 않음.
- 브라우저 `storage` 이벤트로 다른 탭의 시연 데이터 변경을 받으면 열린 예약 폼에서 픽업 시간 선택을 갱신하고, 사라진 가상 요청은 송금 표시 버튼을 비활성화·안내. 결제/확정 기록의 다른 탭 갱신도 표시.
- 기존 꽃집 디자인·사진·고객 상품·가상 송금 표시·수동 확인·상태 전환·월간/일간 캘린더·정원 3건 제한은 그대로 유지.
